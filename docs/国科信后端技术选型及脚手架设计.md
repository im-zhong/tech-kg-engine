### 代码框架

整个工程采用 **Spring Cloud微服务架构**，基于开源的SpringBlade微服务项目制定规则进行开发，主要分为以下几个模块：

- **common** — 全局公共模块，提供缓存、工具类、常量等基础能力

- **auth** — 统一认证中心，支持密码/验证码等多种令牌授予模式

- **gateway** — API网关，负责路由转发、JWT鉴权、请求过滤

- **service** — 核心业务微服务，负责业务管理、系统管理、日志等处理

- **service\-api** — 各服务的Feign接口\+DTO\+VO\+Entity定义，供服务间远程调用

说明：SpringBlade项目具有GVP标识（Gitee 最有价值开源项目）认证，已有20\.8K Starred，访问地址：https://gitee\.com/smallc/SpringBlade/tree/master

# 监控、日志、打点框架

OpenTelemetry是一个开源可观测性框架，由云原生计算基金会（CNCF）维护，用于统一采集和导出系统的指标、日志、链路追踪三类遥测数据 。

[参考资料](https://help.aliyun.com/zh/arms/tracing-analysis/use-managed-service-for-opentelemetry-to-submit-the-trace-data-of-python-applications)

```Plain Text
Java 微服务 (Spring Boot)
  ↓
OTel JavaAgent
  - 自动埋点（HTTP/DB/Redis/Feign 等）
  - 注入日志上下文（trace_id/span_id）
  - 可在网关回传 trace 信息到响应头
  ↓ (OTLP)
OTel Collector（统一接收与处理层）
  ├─ Trace  -> Tempo
  ├─ Metric -> Prometheus
  └─ Log    -> Loki
  ↓
Grafana（统一展示与联动）
```

## 第一层：Java 微服务（Spring Boot）

这是你的业务应用层，比如：

- user\-service

这些服务本来只负责业务逻辑，比如：

- 接收 HTTP 请求

- 调用数据库

- 调用 Redis

- 调用其他微服务

- 输出业务日志

如果没有可观测性方案，这些服务通常只会有：

- 应用日志

- Spring Boot Actuator 指标

- 手工埋点的少量监控

而你的架构里，下一步通过 OTel Java Agent，给这些服务“无侵入”地加上观测能力。

## 第二层：OTel JavaAgent

OTel JavaAgent 是 OpenTelemetry 提供的 Java 探针，启动应用时通过 `\-javaagent` 方式挂载到 JVM 上。

```Plain Text
java -javaagent:opentelemetry-javaagent.jar \
     -Dotel.service.name=order-service \
     -Dotel.exporter.otlp.endpoint=http://otel-collector:4317 \
     -jar app.jar
```

特点：

- 不需要改业务代码或少量改动

- 在运行时增强常见框架

- 自动生成 Trace / Metric / Log 上下文

- 统一通过 OTLP 发给 OTel Collector

也就是说，它像一个“自动埋点器”。

## OTel Collector：统一接收与处理层

OTel Collector 通常负责三类事：

- Receiver：接收数据：接收来自 JavaAgent 的 OTLP 数据

- Processor：处理数据：Collector 可以做很多中间处理，例如：

    - 批处理（batch），把零散数据合并后再发，提高效率、降低网络开销。

    - 资源属性补充（resource）给所有数据补上统一标签：service\.name、service\.namespace、deployment\.environment=prod、region=cn\-east\-1 等等

    - 采样（sampling）：例如 trace 全量太大，可以只保留：错误请求，慢请求，一部分正常请求；

    - 内存保护 / 限流（memory\_limiter）：防止 Collector 自己被打爆。

    - 过滤 / 脱敏：去掉不需要的属性，或者隐藏敏感字段。

- Exporter：导出到后端：把处理后的观测数据分别发往不同系统：Trace \-\&gt; Tempo，Metric \-\&gt; Prometheus，Log \-\&gt; Loki。

## Trace \-\&gt; Tempo

Tempo 主要存 Trace 数据，一条完整 trace 可能包含：

- gateway span

- order\-service span

- mysql query span

- redis span

- inventory\-service span

Tempo 把这些 span 按 trace\_id 聚合后存储。

## Metric \-\&gt; Prometheus

Prometheus 是监控指标系统。

Metric 作用是：整体系统的运动状态

可观测指标，例如：

- 接口 QPS

- P95/P99 延迟
